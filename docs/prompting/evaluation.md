# 效果评估入门

> **一句话结论：** 评估的核心是把“感觉变好了”变成“可比较的记录”：固定一组测试题，先测出基线，每次改 Prompt、换模型或调参数后重跑同一组测试，用分数而不是印象决定采纳还是回滚。

## 前置知识

- 已阅读 [Prompt 入门](/prompting/basics)，知道一个 Prompt 通常包含任务、上下文、格式与约束。
- 已阅读 [推理与解码](/llm/inference-decoding)更好——采样随机性解释了为什么单次输出不足为凭；没读也不影响理解本页。
- 不要求编程；本页示例只用表格和手工推演。

## 学习目标

读完后，你应该能够：

- 解释为什么“试了几个例子觉得不错”不能作为效果结论。
- 为自己的任务建立一个小的固定测试集和基线记录。
- 按任务特点选择评估方式：人工评审、规则指标或 LLM-as-judge。
- 说出公开基准测试（Benchmark）分数与自身任务评估的关系。
- 识别评估中的常见错误：测试题泄漏、只看总分、judge 偏差。

## 核心概念

### 为什么“看起来不错”不可靠

三个原因叠加，让凭印象的判断系统性失真：

- **随机性**：采样参数会让同一个 Prompt 每次输出不同（详见[推理与解码](/llm/inference-decoding)）；一次成功可能只是抽中了好的那种。
- **选择性记忆**：改动之后，成功的例子印象深，失败的例子容易被忽略；没有固定记录，几次之后就不记得真实比例。
- **不可比较**：换模型、改 Prompt、调参数之后，如果输入和评判标准也跟着变，就没有公平的比较基准。

评估要解决的正是这三件事：控制输入不变、控制标准不变、把结果记成可比较的数字。

### 测试集：固定一份考卷

把真实任务里的代表性输入固定下来，形成一份小考卷：

- 规模：认真做可以从 20-50 题起步；本页演示用 10 题是为了篇幅，真实场景太少看不出差异。
- 覆盖：既要有常见情形，也要有边界情形——超长输入、缺少必要信息、容易混淆的说法。
- 标注：每题记下“期望要点”，不一定是唯一标准答案，例如“必须包含退货期限”“必须拒绝报价请求”“输出必须是 JSON”。
- 防泄漏：不要把测试题直接贴进正在迭代的 Prompt 里当示例，也别在同一份考卷上反复“刷题”；用过一段时间的考卷要更换和补充，防止把测试集用成了训练集。

### 指标与基线

先回答“什么叫好”，再动手测：

- **正确性**：答案是否与事实或给定资料一致。
- **完整性**：要求覆盖的要点是否都覆盖了。
- **格式合规**：是否按要求的结构、字段、语言输出。
- **引用可溯源**：声称的来源是否真实存在（RAG 场景的关键指标）。
- **延迟与成本**：Token 消耗、响应时间——它们也是效果的一部分。

能量化才能比较。格式、字段、引用编号这类可以用规则自动检查；语义质量需要人工或模型评判。**基线**是改动前的第一次完整记录：没有基线，任何“变好了”都缺少参照物。

### 三种评估方式

| 方式 | 适合判断什么 | 优点 | 主要局限 |
| --- | --- | --- | --- |
| 人工评审 | 少量高质量判断、最终验收 | 最可信 | 慢、成本高、多人标准会漂移 |
| 规则指标 | 格式、字段、引用、可验证结果 | 快、客观、可自动化 | 覆盖不了语义质量 |
| LLM-as-judge | 语义质量的批量初筛与对比 | 快、可扩展、能给出理由 | 有系统偏差，需人工抽查校准 |

三者通常组合使用：规则指标打底，LLM-as-judge 跑批量，人工评审做抽查和终审。

### LLM-as-judge：让模型当阅卷人

做法：把“待评输出 + 评分标准（量规）”交给一个模型，让它按标准逐项打分并给出理由。量规越具体，judge 越稳定：“按 0-2 分评价回答是否解决了用户的问题，0 = 未解决……”远好于“这个回答好不好”。

judge 也是语言模型，会犯系统性的错，已知偏差包括：

- **位置偏差**：A/B 对比时，评判结果受两个答案的摆放顺序影响。
- **长度偏好**：更长的答案常被打更高分，哪怕信息量相同。
- **自我偏好**：judge 倾向于偏好与自己风格相似的输出。

缓解办法：对比评测时交换顺序各评一次；量规写具体、给例子；定期抽取一部分让人工复核，确认 judge 与人工的口径一致。

### 基准测试分数怎么读

基准测试（Benchmark）是公开的标准考试，例如 MMLU（多领域知识问答）、HumanEval 与 SWE-bench（代码）、GPQA（高难度科学问答）。模型卡上的分数多半来自这类榜单。

公开分数的用途与边界：

- 能用来估计一个模型的大致能力段位，做粗粒度选型。
- 不能直接预测它在你的任务上的表现：考题可能混进了训练数据（数据污染），任务分布也和你的场景不同，何况你的 Prompt 写法与考法并不一样。
- 正确用法：把公开分数当地图，把自己的测试集当考卷——选型时先看地图缩小范围，再用考卷做最终决定。

### 评测驱动的迭代循环

把以上内容连成工作方式：

1. 固定测试集与指标。
2. 跑出基线并记录。
3. 一次只改一处（Prompt、模型或参数）。
4. 重跑整份考卷。
5. 对比分数，决定采纳或回滚。
6. 定期更换、扩充考卷，重新校准 judge。

“一次只改一处”与实验里控制变量是同一件事——同时改 Prompt 又换模型，分数变了也不知道该归功谁。

## 最小推演：10 题考卷对比

虚构任务：客服助手根据产品文档回答售后问题，要求每条答案注明来源文档编号。

| 指标 | 原 Prompt（基线） | 新 Prompt |
| --- | ---: | ---: |
| 要点覆盖（10 题中） | 7 | 9 |
| 格式合规（10 题中） | 8 | 10 |
| 引用真实可溯源（10 题中） | 6 | 9 |
| 平均响应时间 | 3 秒 | 4 秒 |

读表方式比数字本身重要：

- 新 Prompt 在三个质量指标上全面更好，但响应时间变慢——质量提升是用成本换的，要不要采纳取决于业务更在意哪个。
- 引用真实从 6 到 9 的提升幅度最大，说明这次改动主要修正了“编造来源”的问题；这也提示下一轮迭代值得在引用核对上继续投入。
- 10 题只是演示：这么小的样本里，一两题的波动就可能只是随机性。真实测试集要更大，并且要看每题的变化明细，而不是只看总分。

## 对比表

| 做法与概念 | 回答的问题 | 优点 | 主要局限 |
| --- | --- | --- | --- |
| 随手试几个例子 | “这个输出好不好” | 快、零成本 | 有偏、不可比、易被随机性欺骗 |
| 固定测试集 + 基线 | “这次改动有没有变好” | 可比较、可回归 | 需要前期建设与维护 |
| 公开 Benchmark | “模型大致能力段位” | 可横向比较 | 与具体任务有差距、可能数据污染 |
| LLM-as-judge | “大量输出的语义质量” | 快、可扩展 | 有系统偏差，需人工校准 |

## 常见误区

- **“改了 Prompt 看两个例子变好就是变好”**：单次输出受采样随机性影响，少量例子没有统计意义；固定测试集重跑才有可比性。
- **“测试集建好就一劳永逸”**：考卷会泄漏——题目混进示例或被反复“刷题”后，高分不再反映真实能力；要定期更换与扩充。
- **“公开 Benchmark 分数高就一定适合我的任务”**：分数来自别人的考题，存在数据污染与任务分布差异；最终要用自己的考卷验证。
- **“LLM-as-judge 是客观的”**：judge 有位置偏差、长度偏好和自我偏好，只能做初筛，重要决策要人工抽查校准。
- **“只看一个总分”**：总分上升可能掩盖某项退步，比如要点覆盖变好但引用真实性下降；要分指标看。
- **“评估只管质量不管成本”**：延迟、Token 消耗也是效果的一部分；质量提升若以数倍成本为代价，未必值得。

## 自测问题

### 1. 为什么改了 Prompt 之后要重跑整份测试集，而不是只拿新的输出看看？

<details>
<summary>查看答案</summary>

单次输出受采样随机性影响，凭印象无法区分“真的变好”和“这次恰好抽到了好结果”。整份测试集在相同输入、相同标准下重跑，才能和基线公平对比，也才能发现改动在某些题型上造成的退步。

</details>

### 2. LLM-as-judge 有哪些已知偏差？怎样缓解？

<details>
<summary>查看答案</summary>

主要有位置偏差（对比结果受 A/B 顺序影响）、长度偏好（偏长的答案得分偏高）和自我偏好（偏爱自己风格的输出）。缓解：交换顺序各评一次、把评分量规写具体并给例子、定期抽取一部分由人工复核，确认 judge 与人工口径一致。

</details>

### 3. 公开 Benchmark 分数和你自己任务的评估是什么关系？

<details>
<summary>查看答案</summary>

公开分数用于粗粒度选型，估计模型的大致能力段位；它不能预测你的任务表现，因为可能有数据污染、任务分布差异和 Prompt 写法差异。正确做法是先用公开分数缩小候选范围，再用自己任务的固定测试集做最终决定。

</details>

### 4. 哪些指标适合用规则自动检查，哪些必须靠人工或 judge？

<details>
<summary>查看答案</summary>

规则可查的是结构化、可判定的内容：输出格式、必含字段、长度范围、引用编号是否真实存在于资料中。语义质量——回答是否切题、要点是否覆盖、推理是否合理——规则写不出来，需要人工评审，或 LLM-as-judge 初筛加人工抽查。

</details>

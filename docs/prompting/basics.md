# Prompt 入门

> **一句话结论：** Prompt 是交给模型的任务说明与上下文，不是保证结果正确的绝对命令；把要素写清楚、把模型输出当反馈逐轮修改，是普通用户最有效的提升手段。

## 前置知识

- 已阅读 [AI 基础概念](/ai/basics)，知道模型是训练得到的产物；读过 [大模型入门](/llm/basics) 会更顺，但不强制：知道模型逐 Token 生成，也知道幻觉、知识截止这些模型本身的局限。
- 不要求编程经验；本页示例都是可以直接照抄改写的文字。
- 先接受一个边界：Prompt 改善的是模型已有能力的发挥方式，补不了模型本身没有的知识和技能。

## 学习目标

读完后，你应该能够：

- 说出完整 Prompt 的六个构成要素，并判断一段 Prompt 缺了哪个。
- 用结构化写法把一段模糊指令改写成可检查的任务说明。
- 判断 few-shot、思维链这些技巧什么时候有用、什么时候是多余的。
- 解释“不要 X”这类负向约束为什么经常失效，并改写成正向说法。
- 把一次不满意的输出当反馈，定位到具体要素并做有针对性的修改。
- 检查一组少样本示例的格式一致性与答案正确性。
- 用“一次只改一个变量”的纪律做迭代归因，并认出常见的提示词反模式。

## 核心概念

### 一个完整的 Prompt 由哪些要素构成

一段容易得到稳定结果的 Prompt，通常包含六个要素：

- **角色（Role）**：让模型以什么身份处理任务，例如“你是会议记录员”。角色影响语气、详略和取舍标准。
- **任务（Task）**：要模型做什么，用明确的动词开头，一次聚焦一个主任务。“帮我看看这个”不算任务。
- **上下文（Context）**：任务所需的背景，给谁看、用在哪、材料范围和时间版本。只放与任务有关的信息。
- **输出格式（Format）**：列表、表格、Markdown、JSON（一种程序之间传递数据的通用文本格式）或固定的段落结构。需要程序继续处理时，用明确字段或 JSON Schema（一种描述 JSON 数据结构的标准格式）。
- **约束（Constraints）**：必须遵守的规则与边界，包括“怎样才算做好”的完成标准，例如“只用原文信息，无法确认的内容标记为待确认”。
- **示例（Example）**：格式难以用文字描述时，给一个短范例。示例展示结构与判断方式，不是让模型照抄内容。

还有一个特殊的“上下文”来自平台侧：[系统提示（System Prompt）](/glossary#system-prompt)。它是产品或开发者预先设定、长期生效的全局约束，你写的提示是单次任务指令；ChatGPT 的自定义指令、Claude 的项目知识都属于这一类。自己的 Prompt 不生效时，先想想是不是被系统提示盖过了。

把这些要素填进同一个任务：

```text
角色：会议记录员，读者没有参加会议。
任务：把下面的会议记录整理成决策摘要。
上下文：读者需要在 3 分钟内了解结论，只关心决定本身，不关心讨论过程。
输出格式：按"决定、负责人、截止时间、风险"四部分逐条输出。
约束：只使用原文信息；无法确认的标记为"待确认"；每项决定都要能回溯到原文。
示例：决定：上线推迟一周 ｜ 负责人：张三 ｜ 截止：周五前同步新计划 ｜ 风险：影响市场排期
（会议记录粘贴在下方）
```

这比只写“总结一下”更容易得到稳定、可检查的结果。要素不必每次全齐：随口一问可以只有任务；越是重要、要复用或要给程序处理的任务，越应该补齐其余要素。

### 模糊指令改造示范：补齐最容易被漏掉的要素

六要素里，任务和角色最少被漏掉——不说任务就没法开始；最常缺的反而是上下文、输出格式和约束，因为它们看起来“可有可无”。用一个写作任务看三组改造，每组只补一个要素：

| 模糊原句 | 改造后 | 改造点 |
| --- | --- | --- |
| “帮我写一段产品介绍。” | “为下面这份功能清单写一段产品介绍，读者是第一次接触这类工具的小商家，突出能省什么活、上手多快。” | 补的是上下文：读者和用途决定该留什么、强调什么，没有它模型只能写通用套话。 |
| “把这份客户名单整理一下。” | “把名单整理成表格，列依次为姓名、城市、意向等级，按意向等级从高到低排；名单里没有的字段留空，不要推测。” | 补的是输出格式：不规定列名和排序，每次得到的结构都不一样，没法直接用。 |
| “把这段话翻译成英文。” | “把这段话翻译成英文；产品名和专有名词保留英文原文，没有把握的译法在括号里附上中文原词，方便我核对。” | 补的是约束：约束写的是“怎样才算做好”的验收标准，模型有了自查的依据。 |

三组改造的共同点是：每句只补一个要素，改完立刻能看出这个要素带来了什么变化。反过来用也成立——对结果不满意时，先对照六要素问一句“缺的是哪一个”，通常比推翻重写省钱得多。

### 常见技巧什么时候有用：few-shot 与思维链

**[few-shot（少样本示例）](/glossary#few-shot)**是在 Prompt 里给几对“输入-输出”示例，让模型模仿其模式。适合格式转换、风格统一、分类标准难以用文字说清的任务。边界：示例占上下文，堆太多会挤占真正重要的资料；示例本身有偏差，模型会照着学。现代对话模型对常规任务不给示例也能完成——先直接把要求说清楚，不奏效再加示例。

**思维链（CoT，Chain-of-Thought）**是让模型先写出中间推理步骤再给结论，例如“一步一步思考”。直觉：把一步到位的难题拆成多步，每一步的输出又成为下一步的上下文，模型有更多“草稿纸”。适合多步数学、逻辑推理、约束条件多的安排类问题。

什么时候不需要：翻译、总结、事实问答这类单步任务，写出推理过程对正确率帮助不大，反而拉长输出、增加等待和成本。还要记住：思维链只改变“怎么想”，不补充知识——模型本来就不会解的题，写出推理步骤也不等于会解。另外，2026 年的主流旗舰模型已普遍内置思考模式（即推理模型），对它们来说显式写“一步一步思考”基本冗余——直接选用思考/推理档位即可，把提示词的功夫花在六要素上。

### 少样本示例怎么选：一致、覆盖、正确

决定放示例之后，示例的质量就是这类任务结果的上限。挑示例时检查三件事：

- **格式一致**：几条示例用同一种结构与措辞习惯，别一条用表格、一条用段落——示例之间不统一，模型会认为格式本来就是随意的。
- **覆盖边界**：全给“标准情形”的示例，模型学到的只是标准情形的应对；补一条边界示例（缺资料时的问法、应当拒答的输入），模型才知道遇到它们该怎么办。
- **示例本身必须正确**：这是最容易被忽略的一条。模型把示例当“标准答案的样子”来模仿，示例里的错别字、错误归类、错误格式都会被学走，而且往往被稳定复现。给出示例前，先按你自己的标准把它检查一遍。

与零样本的取舍：**零样本（Zero-shot）**——不给示例直接下指令——省 Token、改起来快，适合要求能用文字说清的任务；示例适合“格式与判断标准难以言传”的任务。一个实用次序：先零样本把要求写清楚，格式仍不稳再加示例；加了示例后效果反而变乱，多半是示例之间不一致，而不是示例不够多。

### 为什么“不要 X”经常失效：改说“要 Y”

“不要写太长”“不要用复杂词汇”“不要编造”这类负向约束经常不奏效。直觉解释：模型按条件逐 Token 生成，对“写了什么”的敏感度远高于“没写什么”——“不要 X”提供的只是一个很弱的抑制信号，注意力更多被任务描述里的内容占据，否定词在长 Prompt 里还会被进一步稀释。

改法是把目标说成正向状态：

```text
不要用复杂词汇           →  用初中生能看懂的日常词汇改写
不要编造引用             →  引用必须逐字来自原文，找不到就写"原文未提及"
不要写太长               →  全文控制在 200 字以内
```

负向说法并非完全没用，可以作为补充保留，但不应承担主要约束职责：把模型的注意力引到“该做什么”上，通常比列一串禁令更稳。AI 绘画里专门的负向提示词机制另见下文，它比 LLM 里的“不要 X”有效，但同样只能减少问题、救不了结构缺陷。

### 图像 Prompt 有什么不同

图像 Prompt 负责描述希望生成的视觉内容，常见信息包括：

- 主体：人物、动物、建筑或物体。
- 场景：室内、街道、森林或海边。
- 风格：摄影、插画、动画截图或概念设计。
- 光线：柔光、逆光、霓虹或自然光。
- 构图：特写、全身、广角或俯视。

写法分两种习惯。二次元模型常见标签式：

```text
1girl, solo, school uniform, long hair, blue eyes, classroom, soft lighting
```

支持自然语言的模型（新一代模型多属此类）可以用完整句子：

```text
Create an illustration of a small robot reading a book in a cozy library,
with warm lighting and a calm atmosphere.
```

部分绘画工具（尤其 SD 系生态）提供**负向提示词（Negative Prompt）**，单独填写希望减少的内容：

```text
low quality, blurry, watermark, text, bad anatomy, extra fingers
```

负向提示词适合减少常见质量问题，不能让模型凭空学会训练中没有的能力——底模没学过的概念，提示词和插件都补不上（见[底模是什么](/concepts/base-model)）。生成“不跟手”时按顺序排查：底模是否适合这个题材、提示词是否冲突、[LoRA](/lora/basics) 是否匹配底模、CFG 与采样设置是否按模型卡建议、是否需要 [ControlNet](/concepts/controlnet) 或局部重绘。部件分工详见 [AI 绘画由哪些部分组成](/concepts/components)。

### 迭代修改：一次只改一个变量

把不满意的输出当反馈，最容易犯的错是“一口气改五处”：换了说法、加了约束、补了示例，效果变好了不知道归功于谁，变差了也不知道该撤哪一处。归因的办法与调参一样，一次只改一个要素：改完用同一份输入重跑，与改动前的输出并排放着看——差别是否正是你想要的那一处？想要的效果没出现，说明改的不是症结；想要的出现但别处变坏，说明这个改动有副作用，值得单独权衡。

并排对比时有几个高频副作用值得盯：格式有没有回到老样子（补示例常见）；字数和详略有没有被新约束挤压（补约束常见）；之前答对的内容有没有被改错（换写法常见）。

验证有效的改动别只留在当次的聊天窗口里——把它合回你自己的任务模板，注明这版改了什么、为什么改，模板正是迭代记录的载体（见[工作流和模板区别](/workflows/workflow-vs-template)）。至于改动到底有没有用，用固定考卷验证的方法见[效果评估](/prompting/evaluation)。

### 提示词反模式清单

下面这些写法很常见，但几乎总是在拖后腿：

- **指令互相矛盾**：“要详细，也要简短，重点是全面但别啰嗦”——互相冲突的要求没有优先级时，模型只能自己猜该听哪句，每次猜的还可能不一样。
- **把客套当生产力**：大段“你好呀，麻烦你了，非常感谢”不改变任务条件，只稀释关键信息；礼貌一句话带过即可，篇幅留给上下文和约束。
- **让模型猜输出格式**：通篇不提格式，最后一句忽然说“以表格返回”，格式命中率全凭运气；格式是六要素之一，要写成明确要求。
- **一条 Prompt 塞十个任务**：先翻译、再总结、再起标题、再打分——每个任务都被前面任务的输出干扰，出错也难定位；拆成多轮或多个步骤，每步都拿到完整的六要素。
- **把角色写成简历**：“你是一个擅长数据分析的资深专家”说了模型“是什么”，没说“这次做什么”；角色要落到当前任务的取舍标准上，而不是停留在自我介绍。

## 最小推演：同一任务，差 Prompt 与结构化 Prompt 对照

任务：把一份 800 字的会议记录整理成决策摘要。两种写法并排放：

```text
差 Prompt：帮我总结一下这个会议。
```

```text
结构化 Prompt：（上文六要素版本：角色、任务、上下文、输出格式、约束、示例齐全）
```

逐项对照差在哪：

| 要素 | 差 Prompt | 结构化 Prompt | 缺失的后果 |
| --- | --- | --- | --- |
| 角色 | 无 | 会议记录员，读者没参会 | 详略与口吻没有依据 |
| 任务 | “总结一下”，对象模糊 | 整理成“决策摘要” | 可能输出全文梗概而不是只提决定 |
| 上下文 | 无 | 读者、用途、时间要求 | 无法判断该留什么、删什么 |
| 输出格式 | 无 | 固定四栏 | 每次格式都不一样，没法复用 |
| 约束 | 无 | 只用原文、标注待确认 | 容易补上“合理的推断”，即幻觉 |
| 示例 | 无 | 给一条示例 | 格式全靠模型猜 |

分步看：用差 Prompt 时，模型只能猜——“总结”可以是 100 字梗概，也可以是分条要点；没有约束时，它可能顺手补上记录里没有的内容。结构化版本逐项关小了猜测空间，并且每项决定都能回溯原文，结果可检查。迭代时也一样：输出太啰嗦，改约束；格式不稳，补示例；内容跑偏，补上下文——一次只动一个要素。每轮修改后，用一组代表性样例回归检查：正常输入结果正确；缺资料时明确说不知道；换一种问法格式稳定；引用、计算和外部事实经过实际验证。

这个推演只说明“补齐要素能关小猜测空间”，不保证结果一定正确：记录本身缺的信息，写再清楚的 Prompt 也变不出来。对照实验应该用同一份材料、同一个模型，差异才能归因到 Prompt。

## 对比表

两类 Prompt 服务不同的模型，要素和验证方式差别很大：

| 维度 | 对话模型 Prompt | 绘画 Prompt |
| --- | --- | --- |
| 语言习惯 | 自然语言为主，中文即可 | 英文为主；部分生态偏好标签短句 |
| 核心要素 | 角色、任务、上下文、输出格式、约束、示例 | 主体、场景、风格、光线、构图 |
| 精确控制手段 | 结构化指令、示例、逐轮修改 | 关键词组合、参数、ControlNet 等控制工具 |
| “不要 X”的处理 | 模型敏感度低，改说“要 Y”更有效 | 有专门的负向提示词机制，但同样不是万能 |
| 验证方式 | 用一组样例检查格式与内容 | 固定 seed 做单变量对照，人工挑图 |

共同点也值得记住：两类 Prompt 都是引导而不是命令，模型不一定完全服从；遇到不满意的结果，先怀疑要素缺失，再怀疑模型能力。

## 常见误区

- **“存在万能 Prompt”**：输出质量由模型、资料和任务共同决定，换个模型或换个任务就要重新调整。
- **“要求堆得越多越好”**：要求之间可能互相冲突，不说明优先级时，模型只能自行取舍。
- **“要求输出 JSON 就一定可解析”**：模型可能夹带解释文字、字段名出错，程序侧必须做解析和校验。
- **“复制别人的绘画 Prompt 换个模型照样用”**：不同生态的提示词习惯、标签体系和参数并不通用。
- **“负向提示词是万能修复器”**：它只能减少常见问题，结构缺陷要靠模型、控制工具和后期处理。
- **“Prompt 一次写好就完事”**：输出就是反馈，逐轮修改比一次憋出“完美版本”可靠得多。
- **“没看到效果就多改几处再试”**：同时改多个要素，变好变坏都无法归因；一次只改一个变量，改前改后并排对比，才有资格下结论。
- **“输出不稳定是随机的，管不了”**：多数“不稳定”来自要素缺失——格式没定、约束没写、示例没给，模型只能每次自己发明；先补齐要素，再谈剩下的随机性。

<details>
<summary>查看答案</summary>

模型会把示例当“标准答案的样子”模仿，这条错误分类很可能被稳定复现，甚至被推广到类似输入。防法是在给出示例前先按自己的标准逐条检查：边界情况要么改对，要么删掉。示例的答案正确性与格式一致性同等重要，示例错了，格式再统一也是把错误教给模型。

</details>

### 5. 迭代三轮后效果变好了，但你同时改了写法、约束和示例，想知道到底哪个改动起了作用，怎么办？

<details>
<summary>查看答案</summary>

回退到初始版本，按一次只改一个变量的纪律重新走一遍：每轮只恢复一个改动，用同一份输入与上一版并排对比，就能把贡献归到具体要素上。这次付出的重复劳动换来的教训是：迭代时每轮只动一处，改动记录随手留，归因才不必重来。

</details>

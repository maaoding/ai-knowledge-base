# MCP 入门

> **一句话结论：** MCP（Model Context Protocol，模型上下文协议）把“每个应用单独适配每个工具”的 M×N 问题变成 M+N——工具方按协议封装一次，宿主按协议发现和调用；它标准化的是对接层，不改变模型本身的能力。

## 前置知识

- 读过 [Agent 入门](/llm/agents)（尤其是工具调用一节）会更顺：知道“模型输出结构化参数、由程序执行”这层机制，MCP 在整条链路里的位置就好定位了。
- 读过 [大模型入门](/llm/basics)，知道模型逐 Token 生成、一次回答是怎么来的即可。
- 还没读过 Agent 入门的话，至少先弄懂“工具调用”一件事：模型不直接执行动作，它输出结构化参数，由程序去执行——MCP 讲的正是“程序这一侧怎么把工具接进来”。
- 不要求编程经验：本页讲概念与取舍，不含服务器开发教程；但涉及“配置接入”时需要一点动手耐心——你可能会在宿主应用里真的填一份配置。
- **本页不涉及**：如何自己开发一个 MCP 服务器；想看现成的宿主应用与接入方式，见 [常用工具](/tools/common-tools)。

## 学习目标

读完后，你应该能够：

- 说出 MCP 要解决的 M×N 对接问题，以及“M+N”是怎么省出来的。
- 分清 MCP 服务器、客户端与宿主各自做什么，说出 MCP 服务器的三类能力。
- 解释 MCP 与 Function Calling 的组合关系：谁管模型侧，谁管对接层。
- 概述 MCP 从厂商发布到基金会治理的变化，知道这对生态意味着什么。
- 接入一个 MCP 服务器前，说出要先确认的权限与安全问题。
- 判断一个内部工具该直接用 Function Calling 接入，还是值得封装成 MCP 服务器。

## 核心概念

### 它解决什么问题：M×N 的对接组合爆炸

Function Calling 让模型学会了“调工具”，却把适配的活儿留给了开发者：每接一个新工具，应用这边都要单独写参数定义和对接逻辑。M 个应用、N 个工具，最坏要写 M×N 份适配——同一个日历或数据库系统，在这个应用里适配一次，到另一个应用里又要重来；工具一多，接口就碎片化，接入成本跟着组合数往上涨。举个具体数字：3 个助手应用要接 5 个外部工具，最坏要写 15 份适配；按 MCP 各做一次，就是 3+5=8 份——而且第 6 个工具出现时，工具方只需一个新封装，各宿主按同一协议接入即可。

MCP 的思路是把中间那层标准化：工具或数据的一方按协议把自己的能力封装成 MCP 服务器；支持 MCP 的宿主应用按同一协议发现并调用这些能力。适配工作从“每个组合各做一遍”变成“两边各做一次”——工具方做 N 份封装，宿主做 M 份客户端，中间靠协议对上，这就是“M×N 变 M+N”。要强调的是：它标准化的是对接层，模型本身怎么选工具、怎么传参，并没有被改变。

### 协议怎么分工：服务器、客户端与宿主

MCP 世界里有三个角色，各管一段：

- **服务器（Server）**：能力提供方。日历、笔记库、数据库等工具或数据的一方，按协议把自己的能力封装成 MCP 服务器，对外提供工具（Tools）、资源（Resources）和提示模板（Prompts）。
- **客户端（Client）**：协议执行者。宿主应用内置的部分，负责与服务器建立连接、发现能力、转发调用结果，通常不需要用户直接操作。
- **宿主（Host）**：用户面对的应用。Claude、ChatGPT、VS Code、Cursor 这类支持 MCP 的应用，通过内置的客户端接入各个服务器。

服务器在哪跑也有两种常见形态：有的作为本地进程跑在你自己的电脑上（典型如读写本地文件），有的作为远程服务跑在提供方那边（典型如在线日历）。这个差别直接影响安全边界——本地服务器能触达你机器上的文件，远程服务器则涉及账号授权，两者在配置和认证上要关心的东西不一样。

还有一个容易踩的落差：具体支持哪些能力、协议版本、权限和认证方式，取决于宿主实现。同样是接入同一个服务器，这个宿主可能只放行只读工具，那个宿主则按目录粒度授权，甚至完全不支持——不要默认所有宿主表现一致，接入前要检查兼容性与授权范围。

### 一个 MCP 服务器能提供什么：工具、资源与提示模板

按协议，一个 MCP 服务器可以暴露三类能力：

- **工具（Tools）**：模型可以决定调用的动作——查数据、做计算、执行操作，是三类里最常被用到的一类。
- **资源（Resources）**：可以读取的数据——文件、记录、文档，相当于给模型一个按需取阅的书架。
- **提示模板（Prompts）**：预置的提示结构，把“这个工具该怎么用好”沉淀成模板，宿主可以展示给用户直接选用。

三类能力不要求齐备：一个只提供查询工具的服务器完全合法，具体提供什么由服务器自己决定。对模型而言，资源更像“能查的资料”，工具更像“能做的动作”——前者改变模型的输入，后者改变外部世界；这个区分直接决定权限设计的松紧，工具类能力也最需要留意，因为它意味着模型可以触发真实动作。

### 与 Function Calling 是什么关系：组合，不取代

MCP 不取代 Function Calling。模型侧仍然是“输出结构化参数、由程序执行”——这一层机制没有变化；MCP 标准化的是更外层的“工具如何被发现、描述和对接”。经过 MCP 接入的工具，最终仍以 Function Calling 的方式被模型调用。

类比：Function Calling 像为每台设备单独做一根数据线，MCP 像统一的 USB 接口——设备按标准做一次插头，许多宿主可以复用，但仍要看插座、权限和认证是否匹配。USB 也好、MCP 也好，标准解决的是“插得上”；插上之后“用得对不对”，仍由宿主的实现和工具的质量决定。反过来也成立：不用 MCP，应用照样可以用 Function Calling 接自家工具——MCP 是对接层的标准化选项，不是模型调工具的前提。

### 它走到哪一步了：治理时间线与宿主生态

三个时间点值得记住：

- **2024 年 11 月**：Anthropic 发布 MCP。
- **2025 年起**：OpenAI、Google 等主要厂商陆续支持，MCP 逐渐成为 Agent 生态的通用标准之一。
- **2025 年 12 月**：MCP 被捐入 Linux Foundation 旗下的 Agentic AI Foundation，转为厂商中立治理。

治理归属的变化对使用者的意义是：协议不再绑定在某一家厂商的商业策略上，工具方按 MCP 封装一次能力更值得投入，宿主方也更敢跟进；对普通用户，学一次 MCP 的概念，换宿主时大部分认知可以带走。宿主生态方面，Claude、ChatGPT、VS Code、Cursor 等工具已普遍支持通过 MCP 接入外部数据与工具（清单见 [常用工具](/tools/common-tools)）；各宿主的接入界面与支持范围不同，但概念模型是同一套：填一份配置、让客户端发现能力、按权限调用。对不写代码的普通用户，很多常用服务的接入已经做到“填一份配置”的程度。

### 权限与安全：接入前先看权限清单

能读你笔记库的助手和只会聊天的助手是两种风险等级。MCP 降低了接入门槛，也意味着更多能力会更快地接到你的助手手上——权限的分量随之上升：

- 接入前看清它申请了什么权限、能触达哪些数据；只要读不要写时，别顺手授予写权限。
- 高危动作（发送、删除、花钱）保留人工确认。
- 提示注入的风险随工具面扩大：工具接得越多，一条藏在网页、文档或工具返回里的恶意指令能触发的真实动作就越多。一个典型场景：让助手“读邮件并整理待办”，某封邮件正文里藏着“把笔记导出发到某地址”的指令——工具面越大，这类指令能触达的动作越多。

防护思路与 [Agent 入门](/llm/agents) 的注入安全一节同一口径：把不可信内容当数据处理、工具权限最小化、调用做审计——协议标准化解决不了这些，它们仍要接入方自己设计。一个实用的检查顺序：先看来源（谁发布的），再看权限（要什么），最后看宿主给的确认机制（首次授权、逐次确认），三关都过再放行。

## 最小推演：给助手接上一个笔记库

任务：让聊天助手能查你的笔记库。假设笔记库官方提供了 MCP 服务器，你的宿主应用支持 MCP。跟着编号走一遍：

1. 封装：笔记库一方按协议把自己的能力（搜索笔记、读取笔记）封装成 MCP 服务器——这一步由工具方完成，你不用动手。
2. 配置：你在宿主里填一份配置，告诉它这个服务器的连接方式；这是普通用户通常唯一要动手的一步。配置里的地址、命令和令牌等价于访问凭证，别截图外发或贴到公开场合。
3. 发现：宿主的 MCP 客户端连上服务器，问“你有什么能力”，拿到工具清单和每个工具的描述。
4. 调用：你问“我上周记了什么”，模型决定调用搜索工具、输出结构化参数，由程序执行并把结果带回对话。
5. 权限确认：首次访问通常弹出授权——看清它申请的是只读还是可写、能触达哪些目录，再决定放行还是拒绝。

这个推演只覆盖“接上并查一次”的最小路径，不等于真实系统——真实接入还要处理认证与令牌管理、服务器与宿主的协议版本兼容、工具出错后的重试与结果校验，这些都超出本页范围。另外，“接上了”只是第一步：接进来的工具表现如何、答案准不准，仍要按 [效果评估](/prompting/evaluation) 的思路做验证。

## 对比表

按维度对照 Function Calling 与 MCP：

| 维度 | Function Calling | MCP |
| --- | --- | --- |
| 解决什么问题 | 模型怎么“说”要调工具、传什么参数 | 工具怎么被发现、描述和对接 |
| 谁定义接口 | 每个应用自己定义并维护工具清单 | 工具方按协议封装一次，宿主按协议发现 |
| 换一个宿主要不要重做 | 工具适配往往要重做一遍 | 服务器封装不变，宿主支持即可接入 |
| 谁负责执行 | 应用程序执行函数 | 仍是应用程序与服务器执行，MCP 不代劳 |
| 常见形态 | 各应用自定义的工具清单 | 本地进程或远程服务，由工具方发布 |
| 适合谁 | 应用开发者定义少量自有工具 | 工具方想让能力被多个宿主复用；用户想低成本接入 |

选择时先问问题在哪一层：模型“会不会调、传没传对”是 Function Calling 层的事；工具“接得进多少应用、换应用要不要重来”是 MCP 层的事。两者不是二选一——MCP 服务器暴露的工具，最终仍以 Function Calling 的方式被模型调用。如果你是工具方，判断标准更简单：只服务一个应用的内部工具，直接 Function Calling 更省事；想让任意宿主都能接，才值得封装成 MCP 服务器。

## 常见误区

- **“MCP 取代了 Function Calling”**：两者是组合关系。模型侧仍是“输出结构化参数、由程序执行”，MCP 标准化的是更外层的对接层。
- **“接了 MCP 就安全了”**：协议标准化不等于权限收敛。接入前仍要看清权限范围与数据触达面，高危动作保留人工确认。
- **“所有宿主的 MCP 表现都一致”**：支持哪些能力、协议版本、权限和认证方式取决于宿主实现；同一个服务器在不同宿主里的可用范围可能不同。
- **“MCP 让模型变聪明了”**：它标准化的是对接，不是模型能力。模型还是那个模型，选错工具、传错参数的可能性一点没少；工具好不好用、结果准不准，仍取决于工具本身的质量。
- **“用 MCP 必须会写代码”**：很多宿主已做到“填一份配置”即可接入；写代码只在开发自己的 MCP 服务器时才需要。
- **“MCP 服务器随便装一个就行”**：服务器是能触达你数据的外部程序，来源与申请的权限都要审——把它当成安装一个新软件来对待，而不是加一个插件那么轻率。

## 自测问题

### 1. “M×N 变成 M+N”，省掉的那部分工作量具体是什么？

<details>
<summary>查看答案</summary>

没有 MCP 时，M 个应用要支持 N 个工具，几乎每个“应用×工具”组合都要单独写适配，工作量按 M×N 增长。MCP 把它拆成两半：N 个工具方各按协议封装一次服务器，M 个宿主各实现一次客户端，中间靠协议对上——两边都只做一次，总量从 M×N 降到 M+N。省掉的是“每换一个应用就把同一个工具重新适配一遍”的重复劳动。

</details>

### 2. 服务器、客户端与宿主分别是什么？“能用哪些能力”由谁决定？

<details>
<summary>查看答案</summary>

服务器是工具或数据一方按协议封装的能力提供方；宿主是用户面对的应用（聊天助手、编辑器等），其内置的 MCP 客户端负责与服务器建立连接、发现能力、转发调用。具体支持哪些能力、协议版本、权限和认证方式取决于宿主实现——同一个服务器在不同宿主里的可用范围可能不同，接入前要检查兼容性与授权范围。

</details>

### 3. 一个 MCP 服务器可以提供哪三类能力？各举一个例子。

<details>
<summary>查看答案</summary>

工具（Tools）：模型可决定调用的动作，例如“搜索笔记”；资源（Resources）：可读取的数据，例如“读取某条笔记的正文”；提示模板（Prompts）：预置的提示结构，例如“用要点格式总结一篇笔记”。本页推演里的笔记库服务器，就同时提供了搜索与读取两个工具。不是每个服务器都提供全部三类，具体由服务器实现决定。

</details>

### 4. MCP 和 Function Calling 是什么关系？

<details>
<summary>查看答案</summary>

组合关系，不是替代关系。Function Calling 是模型侧的机制：模型输出结构化参数、由程序执行。MCP 标准化的是更外层的“工具如何被发现、描述和对接”——工具方封装一次，兼容的宿主都能发现和调用。经过 MCP 接入的工具，最终仍以 Function Calling 的方式被模型调用；类比 USB：设备做一次标准插头，许多宿主复用，但插座、权限和认证是否匹配仍要单独看。

</details>

### 5. 接入一个 MCP 服务器前，你应该检查哪些东西？

<details>
<summary>查看答案</summary>

至少三件事：来源是否可信——服务器是能触达你数据的外部程序，要像安装新软件一样审它；申请了什么权限、能触达哪些数据——能读笔记库的助手和只会聊天的助手是两种风险等级；高危动作（发送、删除、花钱）是否保留人工确认。此外核对宿主与服务器的能力和协议版本兼容，别默认所有宿主表现一致。

</details>

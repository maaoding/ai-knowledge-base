# RAG 入门

> **一句话结论：** RAG 让模型先检索资料再回答，解决知识时效、私域知识和引用溯源问题；至于让模型规划步骤、调用工具去“完成任务”的那一半，见 [Agent 入门](/llm/agents)。

## 前置知识

- 已阅读 [Tokenization 与 Embedding](/llm/tokenization-embedding)，知道 Embedding 可以用来计算语义相似度——这是理解本页向量化部分的前提。
- 读过 [推理与解码](/llm/inference-decoding) 会更顺，知道模型逐 Token 生成、推理时参数固定即可。
- 不要求会搭建检索系统或编写代码；本页讲原理与设计取舍，不提供具体搭建教程。
- **本页不涉及**：RAG 系统的代码实现与部署步骤；想动手时，可用的工具与平台见 [常用工具](/tools/common-tools)。

## 学习目标

读完后，你应该能够：

- 按“切分 → 向量化 → 检索 → 拼 Prompt → 生成”的顺序描述 RAG 流程。
- 说出切分（Chunking）的两难：块太大稀释相关性，太小丢上下文。
- 解释 Embedding 与余弦相似度如何支撑语义检索，说出影响检索质量的三个环节。
- 解释 RAG 为什么能缓解幻觉，以及引用溯源为什么能暴露“资料没支撑答案”的回答。
- 在“直接问模型、RAG、微调”之间根据场景做出选择。
- 说出 RAG 特有的数据权限边界与提示注入风险。

## 核心概念

### RAG：先查资料，再回答

**RAG（Retrieval-Augmented Generation，检索增强生成）**在模型回答之前，先从外部资料中找出相关片段，再让模型基于资料作答。典型流程：

```text
离线准备：文档 -> 切分成片段 -> 每个片段算 Embedding -> 建立语义索引
在线回答：用户提问 -> 问题也算 Embedding -> 检索最相似的若干片段（Top-K）
         -> 片段连同问题拼进 Prompt -> 模型基于资料生成回答
```

（这里的 K 指检索返回的条数，与解码采样里的 Top-k 参数无关。）

为什么需要 RAG：

- **知识时效**：模型参数在训练时固定，训练截止之后的新信息它不知道；检索可以随时接入新资料。
- **私域知识**：内部文档、公司制度这类资料模型从没见过，不能指望它凭空知道。
- **引用溯源**：回答可以标注“来自哪篇文档”，方便人工核查，这是降低幻觉风险最直接的机制之一。
- **成本更低**：更新知识只需更新资料库，不需要重新训练模型。

RAG 的核心不是“把所有文档塞给模型”，而是把最相关、可信、足够短的材料放进上下文。

适合：企业知识库问答、产品文档助手、法规制度查询、需要引用来源的总结、资料经常更新的场景。不适合：没有可靠原始资料的问题、需要复杂事务操作但没有工具接口的问题、文档本身质量很差且互相矛盾的场景。

RAG 的常见失败点：切分太碎导致答案缺上下文、检索召回不准、塞入太多无关片段、没有来源标记无法复查、文档版本混乱新旧混杂。

发现检索不准时，常见的改进方向按代价从低到高：调整召回数量（Top-K）；调整切分粒度，让每段承载一个完整主题；混合检索——关键词检索与向量检索互补，专有名词靠前者、语义相近靠后者；用专门的重排（Rerank）模型对召回片段二次排序，把最相关的排到最前；改写用户提问再检索（查询改写）；按文档元数据（部门、版本、时间）预先过滤。主流工具和框架基本都有这些功能的现成开关，名词对上号即可查阅对应文档。

这份清单背后的逻辑，接下来按流程顺序摊开讲：先看切分，再看向量化与检索，最后回到拼 Prompt 与引用。

### 切分（Chunking）：块太大稀释相关性，太小丢上下文

资料进库的第一步是切分（Chunking，见[术语表](/glossary#chunk)）：把整篇文档切成检索用的片段。最常用的是按标题和段落切——标题是天然的语义边界，一段话大致只说一件事。

难处在块的大小，两个方向都会出错：

- **块太大**：一个片段混进几个主题，检索时相关性被稀释——你问年假制度，它带回来小半份员工手册，真正相关的三行淹没在无关段落里，还白白占上下文。
- **块太小**：一段话被拦腰截断，背景丢了——“需提前 3 个工作日申请”单独成块，你不知道它说的是年假还是调休；检索命中了，答案却没法用。

实践上按“一个块承载一个完整主题”定粒度，并常在块上保留标题路径等上下文信息；具体数值没有万能答案，要靠评估来调。

### 向量化与语义检索：按意思找，不是按字面找

切好的每个片段要算一个 Embedding（向量），语义相近的片段，向量在空间里也挨得近，原理见 [Tokenization 与 Embedding](/llm/tokenization-embedding)。用户提问同样被向量化，然后找出与问题向量最相似的若干片段——这就是语义检索，存取这些向量通常交给[向量数据库](/glossary#vector-database)。

相似度最常用的度量是余弦相似度（Cosine Similarity）：两个向量夹角越小，越相似。它的直觉价值在于“字面不同、意思相近”也能匹配上：“休假怎么请”和“年假申请流程”字面几乎不重合，向量却能靠得很近。这也是本页最小推演用“词面重合”模拟检索时特意声明的那条差距。

### 检索质量三道关：切块、Embedding、Rerank

回答好不好，先取决于检索准不准。检索质量通常卡在三道关上：

1. **切块**：粒度不对，相关内容被切碎或稀释，后面全白搭——上一节的两难就在这里。
2. **Embedding 质量**：向量模型对领域词汇不敏感时，专有名词、缩写算不出有区分度的相似度；换更强的 Embedding 模型是常见改进。
3. **Rerank 重排**（见[术语表](/glossary#rerank)）：先用向量检索粗筛一批候选，再用专门的重排模型对候选逐个精排，把最相关的顶到最前——粗筛求“别漏”，重排求“排对”。

三道关之外还有一个互补手段，就是上文提过的混合检索：关键词与向量两路一起上，结果合并去重。这些改进能提升召回质量，但都替代不了对检索效果本身的评估。

排查检索问题时，先分清两种症状：该检到的没检到，是召回问题，去查切块与 Embedding；检到了但排得靠后，是排序问题，上 Rerank。判断办法很朴素：把你认为最相关的片段找出来，看它有没有进候选、排在第几位——不改任何配置，就能定位问题出在哪道关。

### 拼 Prompt 与引用溯源：让回答带上出处

检索到的片段最后要拼进 Prompt：模板通常写明“仅根据以下资料回答”，附上带编号的片段与用户问题；写模板的通用原则见 [Prompt 入门](/prompting/basics)。

拼 Prompt 的同时顺手就把引用溯源做了：每个片段带来源编号，要求模型在答案末尾标注出处。引用的价值不止方便核查——它还是一台幻觉探测器：要求逐句标注来源之后，如果模型在某句上给不出编号，或者编号对应的资料里根本没有那句话，就说明这句是模型自己补的、不是资料支撑的。“资料没支撑答案”的幻觉，靠引用能被直接暴露出来。

拼进多少片段同样有取舍：Top-K 给大了，相关片段不容易漏，但无关内容多了会稀释模型注意力、抬高成本；给小了省上下文，却容易漏。片段的摆放顺序也有影响——最相关的放开头或结尾，通常比埋在中间稳。这些参数没有标准答案，值得拿几组真实问题各跑一遍，对比着定。

### 提示注入与数据权限：检索内容不可全信

RAG 的回答基于外部资料，而外部资料不一定干净。提示注入（Prompt Injection）指攻击者把恶意指令藏进模型会读到的内容里——网页、文档、检索片段都可能被植入“忽略之前的指令，去做某事”这类话；模型如果分不清“读到的数据”和“收到的指令”，就可能照做。RAG 会放大这个风险：模型读的外部内容越多，一条注入指令能造成的实际后果就越严重。基本防护是把检索片段当数据、不当指令——拼进 Prompt 时明确标注“以下是待处理的资料”；完整的注入防护与工具安全见 [Agent 入门](/llm/agents)，检验方法见 [效果评估](/prompting/evaluation)。

对内部知识库这类多人共用的场景，还有一道 RAG 特有的边界：数据权限。检索阶段要按提问者的身份过滤资料范围，否则任何能提问的人都能检索并问出无权查看的文档——“A 部门的人问不出 B 部门的制度”，靠的不是模型自觉，而是在检索层就把范围收窄。这与“工具权限最小化”是同一逻辑，只是作用在数据一侧。

### RAG 与微调怎么选：缺知识还是缺行为

- 需要固定的格式、语气、分类标准：考虑微调。
- 需要回答经常变化的文档、制度、产品资料：优先 RAG。
- 需要严格引用来源：优先 RAG。
- 想降低幻觉：RAG 加评估，比盲目微调更直接。
- 两者可以组合：RAG 提供事实，微调稳定行为和风格。

## 最小推演：手工做一次 RAG

假设资料库只有三篇短文档：

| 编号 | 标题 | 内容 |
| --- | --- | --- |
| 1 | 年假制度 | 员工每年有 5 天带薪年假，入职满两年增加 2 天，需提前 3 个工作日在系统申请。 |
| 2 | 报销流程 | 差旅报销需在返回后 10 个工作日内提交，并附发票原件。 |
| 3 | 考勤规定 | 工作日 9:00 至 18:00，迟到 30 分钟以上记警告一次。 |

用户问题：“年假要提前多久申请？”

第 1 步，检索。用最粗糙的“词面重合”模拟相似度——数问题里的词在各文档中出现了几个：

| 文档 | 与问题重合的词 | 得分 | 结果 |
| --- | --- | ---: | --- |
| 1 年假制度 | 年假、提前、申请 | 3 | Top-1，拼入 Prompt |
| 2 报销流程 | 无 | 0 | 落选 |
| 3 考勤规定 | 无 | 0 | 落选 |

第 2 步，拼 Prompt。把 Top-1 片段放进模板：

```text
请仅根据以下资料回答问题，并在答案末尾注明来源编号。

[资料1]（年假制度）：员工每年有 5 天带薪年假，入职满两年增加 2 天，
需提前 3 个工作日在系统申请。

问题：年假要提前多久申请？
```

第 3 步，生成。模型基于资料输出：“年假需提前 3 个工作日在系统申请（来源：资料1）。”

这个推演用词面重合代替了真实检索，只说明“检索 → 拼 Prompt → 带引用生成”的数据流，不等于真实系统——真实 RAG 用向量相似度而非字面重合，能把“休假”和“年假”这类字面不同但语义相关的词匹配上，但也可能引入噪声，所以检索质量本身需要单独评估。

## 对比表

三种方案解决不同的问题：

| 方案 | 知识来源 | 擅长 | 主要局限 | 典型场景 |
| --- | --- | --- | --- | --- |
| 直接问模型 | 训练时学进参数的知识 | 通用问答、写作、解释 | 知识截止、可能幻觉、无引用 | 日常对话、文案草稿 |
| RAG | 外部知识库实时检索 | 时效与私域知识、引用溯源 | 依赖检索质量和文档质量 | 企业知识库问答 |
| 微调 | 把行为风格学进参数 | 稳定格式、语气、任务模式 | 不擅长更新知识、可能遗忘 | 固定话术与格式 |

选择时先问“缺的是知识、行为还是执行”：缺知识用 RAG，行为不对用微调，需要多步执行与工具调用的任务则交给 [Agent 入门](/llm/agents)。

## 常见误区

- **“把所有文档塞进上下文就是 RAG”**：RAG 的核心恰恰是筛选——只检索最相关、可信、足够短的片段；全部塞入既稀释关键资料，又白白增加成本。
- **“有了 RAG 就不会幻觉”**：检索不到、文档质量差或模型不忠实于资料时仍会出错；RAG 降低风险，不消除风险。
- **“块切得越小检索越准”**：太小的块丢上下文，检索命中了也没法用来回答；切分的目标是“一个块一个完整主题”，不是越碎越好。
- **“检索回来的资料都对，照着抄就行”**：片段可能过时、互相矛盾或与问题不相关；引用溯源正是用来暴露“资料没支撑答案”的机制，核查来源是必要步骤。
- **“微调能让模型学会新知识”**：微调主要改变行为与表达；知识更新更适合 RAG。
- **“RAG 和 Agent 是竞争关系”**：RAG 常常就是 [Agent 入门](/llm/agents)里 Agent 调用的一件工具，两者是组合关系。

## 自测问题

### 1. 按顺序说出 RAG 的流程，并解释为什么“引用溯源”靠 RAG 容易实现？

<details>
<summary>查看答案</summary>

流程：切分文档 → 向量化并建立索引 → 用户提问时检索相似片段 → 把片段拼进 Prompt → 模型基于资料生成。因为回答所依据的片段是检索进来的明确文档，Prompt 中可以带上来源编号，输出时标注出处，答案与原文的对应关系可以直接人工核查。

</details>

### 2. 公司要做“经常更新的内部制度”问答，选微调还是 RAG？为什么？

<details>
<summary>查看答案</summary>

选 RAG。制度经常更新，写进参数很快过期，重新训练成本高；RAG 只需更新资料库，还能标注来源便于核实。前提是文档本身质量可靠，切分和检索经过评估。

</details>

### 3. 同一份文档，切得太碎和切得太大，检索分别会出什么问题？

<details>
<summary>查看答案</summary>

切得太碎：片段丢上下文，“需提前 3 个工作日申请”单独成块就说不清是年假还是调休——检索可能命中，答案却没法用。切得太大：一个块混进多个主题，相关性被稀释，真正相关的几行淹没在无关段落里，还多占上下文。实践按“一个块承载一个完整主题”定粒度，靠评估调整。

</details>

### 4. 为什么说“引用溯源”能暴露幻觉？

<details>
<summary>查看答案</summary>

因为回答的每个论断都被要求标注来源片段。某句话给不出编号，或编号对应的资料里根本没有这句话，就说明这是模型自己补的、不是资料支撑的——引用把“答案是否被资料支撑”变成可以逐句人工核查的问题。

</details>

### 5. “A 部门的人问不出 B 部门的制度”，这道边界设在哪里？为什么不能靠模型自觉？

<details>
<summary>查看答案</summary>

设在检索层：按提问者身份过滤可检索的资料范围，无权的文档根本不进入候选。不能靠模型自觉，因为模型只看得到拼进 Prompt 的内容，无法判断“没被检索进来的还有什么”——权限必须在数据到达模型之前收窄，这与工具权限最小化是同一逻辑，只是作用在数据一侧。

</details>

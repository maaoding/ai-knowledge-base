# 量化与本地部署

> **一句话结论：** 量化（Quantization）就是用更少的比特存同一份模型权重，让消费级硬件装得下原本装不下的模型；但“装得下”只是第一步——显存要算总账（权重、KV Cache、框架开销三笔相加），本地还是 API 则要算另一本账（隐私、成本、能力上限、维护）。两笔账都能手算出数量级，本页就是把这两笔账讲清楚。

## 前置知识

- 已阅读 [大模型入门](/llm/basics)，知道“7B”“14B”指参数量级，模型能力大体随规模增长。
- 已阅读 [推理与解码](/llm/inference-decoding)，记得两条结论即可：KV Cache 会随上下文变长而占用更多显存；上下文窗口是模型单次推理能处理的 Token 总量。本页直接引用这两条，不再展开机制。
- 不要求动手：本页只讲原理与算账，不含任何安装与运行命令；可上手的工具对比见 [常用工具](/tools/common-tools)。
- 先接受一个边界：本页所有显存数字都是“约”数，目的是建立数量级直觉，不替代实测。

## 学习目标

读完后，你应该能够：

- 用一句话说清量化在做什么，以及它为什么通常不会把模型“压坏”。
- 分清精度档（FP16/INT8/INT4）、量化方法（GPTQ/AWQ）与文件格式（GGUF）这三层概念。
- 用“参数量 × 每参数字节数”手算权重显存，再叠加 KV Cache 与开销得出总账。
- 说出 NVIDIA 显卡、Apple Silicon、CPU 三类硬件路线各自的长处与边界。
- 面对一个具体任务，用判断清单决定本地部署还是调 API。

## 核心概念

### 它解决什么问题：好模型太大，你的显卡装不下

开放权重模型（常被泛称为开源模型）的参数量从几十亿（7B 量级）到几百 B 不等，而训练与默认推理精度是 FP16——每个参数用 16 位浮点数存储，折合 2 字节。做个乘法：一款 7B 模型，光权重就要约 14GB 显存（VRAM）；几百 B 的模型则要几百 GB，远超一块消费级显卡的显存——常见档位大致在 8GB 到 24GB 之间。

**量化（Quantization，词条见[术语表](/glossary#quantization)）**做的事说穿了很简单：用更少的比特存同一份权重。每个参数从 2 字节压到 1 字节（INT8）甚至半字节（INT4），同一块卡能装下的模型就大了好几倍，消费级硬件第一次有了“选择权”。本地部署的动机也随之清楚：数据不出本机、离线可用、没有按量账单；代价同样先说在前面——参数规模与量化都会压低能力上限，升级排错要自己动手。云端与本地的逐维度对比表见 [常用工具](/tools/common-tools)；本页负责把“本地这条路能走多宽”算清楚。

### 量化的直觉：用更少的比特存同一份权重

为什么把每个参数从 16 位压到 4 位，模型通常还不至于“变傻”？直觉是这样的：模型的几十亿个权重是一大堆数值上大同小异的浮点数，这种分布里存在大量冗余。量化相当于把连续的数值“四舍五入”到一档更粗的刻度上——刻度粗了，每个数都带一点误差，但模型的能力分布在海量参数上，单个参数的小误差多数时候会被相互抵消。所以对问答、写作、翻译、总结这类日常任务，质量损失通常有限。

代价也要说在明处：对精度敏感的任务，损失更明显——数学推理、代码生成、小语种，这些场景里数值误差更容易被放大。而且量化越激进（比特数越少），风险越大：FP16 到 INT8 通常几乎无感，FP16 到 INT4 就值得实测了。怎么实测？用固定测试集对比量化前后的输出，方法见 [效果评估](/prompting/evaluation)——别凭感觉下结论。

### 三层名字怎么分清：精度、方法与格式

下载模型时你会撞见一串名字：INT4、GPTQ、AWQ、GGUF、Q4_K_M……零基础的读者最容易把它们当成同一类东西。其实它们分属三层：

```text
一份量化模型文件的名字里，通常叠着三层信息：
  精度档：  FP16 / INT8 / INT4  —— 决定每个参数用几个比特存（压到多细）
  量化方法：GPTQ / AWQ          —— 决定用什么算法去压（怎么压）
  文件格式：GGUF                —— 决定压完存成什么文件、哪个生态能读（在哪用）
```

**精度档**回答“压到多细”：FP16 是 16 位浮点，训练与默认推理精度，体积与质量的基准点；INT8 是 8 位整数，体积减半；INT4 是 4 位，再减半。档位越低，体积越小、速度往往越快，质量风险越高——它就是一根以质量换体积的滑杆。

**量化方法与文件格式**回答“怎么压、在哪用”。GPTQ 与 AWQ 是两类训练后量化（Post-Training Quantization）方法：模型训练完参数不再动，由算法把权重压到低精度；两者都主要面向 GPU 推理生态，AWQ 对激活分布更友好一些。GGUF 则不是方法，是文件格式——llama.cpp 生态的模型文件都存成它，也是 CPU 与 Apple Silicon（统一内存）上混合推理的主力格式，文件名里的 Q4_K_M 这类标记就是它内含的量化等级。

判断句只有一条：**选格式先看你的硬件**——NVIDIA 显卡生态多见 GPTQ/AWQ，Mac 或纯 CPU 路线基本是 GGUF。三层的完整对比已并排放在下文对比表里；而“你的硬件到底带不带得动”，是下一节要手算的账。

### 显存怎么估：一笔可以手算的账

“这块卡带得动吗”不是感觉问题，是加法问题。显存总账 = 权重 + KV Cache + 框架开销，三笔分开算：

**第一笔：权重。** 参数量 × 每参数字节数，这是大头。以 7B 模型为例：FP16（2 字节）约 14GB；INT8（1 字节）约 7GB；INT4（0.5 字节）约 3.5GB。这里每个数字都要读成“约”：文件里还有词表等额外成分，GB 与 GiB（十进制与二进制单位）之间还有约 7% 的口径差——但数量级不会变，而数量级正是这笔账的用途。

**第二笔：KV Cache（词条见[术语表](/glossary#kv-cache)）。** 它为什么能加速生成、机制如何，在 [推理与解码](/llm/inference-decoding) 展开，这里只引用结论：KV Cache 随上下文长度增长，也随并发请求数（批大小，Batch Size）成倍增长。量级感受：7B 模型在几千 Token 的上下文下，KV Cache 常在 GB 量级；上下文拉到几万 Token，它能追上甚至超过权重本身。上下文能开多长，受模型的[上下文窗口](/glossary#context-window)上限约束——窗口开多大，这笔账就按多大算。顺带一提：KV Cache 本身也能量化压缩，用一点精度换占用，工程上同样常见，知道有这根旋钮即可。

**第三笔：框架开销。** 推理框架与运行时自身要占一两 GB，加上计算过程中的各类缓冲，通常再预留 1–2GB 余量比较稳妥。

三笔加总，才叫“装得下”。**最常见的翻车是只算了权重**：装上能跑，一拉长上下文或多开一个并发就爆显存——不是模型的问题，是总账没算完。算完发现不够怎么办？顺序通常是：先降精度档（FP16 → INT8 → INT4），再砍上下文与并发，最后才考虑换硬件——三笔账里，权重档位是最好拧的旋钮。

### 硬件与工具的边界：三类路线

同一份量化模型，在不同硬件上走的是不同路线，各有各的天花板：

- **NVIDIA 消费级显卡**：生态最全的一类，GPTQ、AWQ、GGUF 都能跑，推理框架支持最成熟。边界在显存档位：8GB 只够小模型加短上下文，16GB 从容许多，24GB 能覆盖大多数日常需求。
- **Apple Silicon（Mac）**：长处在统一内存（Unified Memory）——CPU 与 GPU 共享同一大块内存，没有“显存”这个单独的小池子，所以 Mac 跑大参数量化模型反而顺，生态以 GGUF 为主。边界是速度受内存带宽限制，且游戏显卡那套生态（GPTQ/AWQ）基本不在它这边。
- **CPU 推理**：零门槛——任何现代电脑都能跑，但速度最受限，适合小参数模型与低频使用，作为“先跑通、建立直觉”的起点完全合格。

工具层一句话带过：Ollama、LM Studio 这类工具把“选模型、下量化版本、跑起来”封装成一步，底层引擎多为 llama.cpp；工具之间怎么选、隐私与费用怎么对比，见 [常用工具](/tools/common-tools)，本页不重复。

### 本地还是 API：一张判断清单

工具解决“怎么跑”，本节回答更前面的一个问题：什么时候值得把模型搬到本地。判断信号分两边列。

值得本地的信号：

- **数据敏感，不能出本机**：隐私是硬约束时，其他考虑都往后排。
- **离线或网络受限**：断网也要能用的场景，没有替代选项。
- **调用频繁，且任务在开源模型能力圈内**：高频调用才能把一次性硬件成本摊薄；先确认开源模型在你这类任务上确实够用。
- **已有闲置硬件**：边际成本接近电费，试错几乎免费。

API 更划算的信号：

- **要最强能力与最新知识**：云端最强模型与本地量化模型的能力差距是现实存在的。
- **低频使用**：硬件折旧与折腾时间摊不薄，按 Token 付费更便宜。
- **不想运维**：升级、排错、环境管理都是隐性时间成本，API 把这些外包给了服务商。
- **任务对质量波动敏感**：量化与参数规模带来的质量波动，会原样传导进你的产出。

两边不是单选题，常见的中级路线是混合：**本地小模型做粗活**（分类、打标、草稿），**API 做关键步骤**（最终成稿、复杂推理）。举两个例子：医院内部文档问答——数据敏感加高频调用，指向本地；每月写两篇深度报告——要最强能力加低频，指向 API。成本结构上，本地是一次性硬件加电费，API 是按 Token 付费，长上下文会放大后者——两种形态的逐项对比见 [常用工具](/tools/common-tools) 的对比表，本页的清单负责把信号对号入座。

顺带一句边界：如果你想通过微调让模型更贴合自己的任务，那是另一本资源账，属于训练侧，见 [训练、微调与对齐](/llm/training-alignment)；本页只管推理与部署。

## 最小推演：一块 16GB 显存的卡，带得动 14B 模型吗

给定：一块 16GB 显存的显卡，一款 14B 模型，日常使用按几千 Token 的上下文算。问：FP16、INT8、INT4 三种精度各要多少显存？跟着编号算：

1. **先算权重**：14B 乘每参数字节数。FP16（2 字节）约 28GB——远超 16GB，直接出局。INT8（1 字节）约 14GB——还没算另外两笔就已占掉近九成，装不下或踩在极限上。INT4（0.5 字节）约 7GB——不到一半，明显有余量。
2. **再算 KV Cache**：几千 Token 的上下文，按 GB 级预留，取 1–3GB（具体取决于模型结构与上下文长度）。
3. **加框架开销**：预留 1–2GB。
4. **加总判断**：INT4 约 7 + 2 + 2 ≈ 11GB，可行且留有余量；INT8 约 14 + 2 + 2 ≈ 18GB，超出 16GB，勉强或装不下；FP16 约 28GB 起，无缘。
5. **检查隐蔽变量**：把上下文从几千拉长到几万 Token，KV Cache 会从 GB 级一路涨到能追上权重的量级——第 4 步里 INT4 的“有余量”就被吃成“没余量”。

结论：这块卡跑 14B，选 INT4 并控制上下文长度；INT8 勉强；FP16 无缘。

边界声明：真实数字随模型结构（层数、注意力实现等）、具体量化等级与推理框架而变，这笔账只做数量级判断，不替代实测。

## 对比表

把本页的两张核心表并排放在一起。

**表一：精度档——“压到多细”的滑杆**

| 精度档 | 每参数体积 | 质量 | 速度 | 典型场景 |
| --- | --- | --- | --- | --- |
| FP16 | 2 字节（基准） | 基准 | 基准 | 训练，以及显存充裕时的默认推理精度 |
| INT8 | 1 字节（约一半） | 损失通常很小 | 往往更快 | 显存紧张但想贴近原精度 |
| INT4 | 0.5 字节（约四分之一） | 日常任务够用，敏感任务需实测 | 往往更快 | 消费级硬件跑大参数模型的主力档 |

**表二：量化方法与文件格式——“怎么压、在哪用”**

| 名称 | 类别 | 面向生态 | 一句话定位 |
| --- | --- | --- | --- |
| GPTQ | 训练后量化方法 | GPU 推理生态常用 | 训练完成后用算法把权重压到低精度的代表性方法 |
| AWQ | 训练后量化方法 | GPU 推理生态常用 | 同为训练后量化，对激活分布更友好 |
| GGUF | 文件格式 | llama.cpp 生态，CPU 与 Apple Silicon 的主力 | 文件即模型，文件名内含量化等级标记（如 Q4_K_M） |

一句话分工：**精度档就是那根体积与质量的滑杆，方法与格式决定这份滑杆在哪个生态里拧**。建议的顺序是先定格式（看硬件），再定档位（看显存总账与质量要求）。

## 常见误区

- **“量化到 4 位质量就腰斩”**：多数日常任务损失有限；真正要警惕的是数学、代码、小语种这类精度敏感任务。等级越激进越要实测，别一刀切。
- **“显存只要装下权重就行”**：KV Cache 与框架开销被漏算，上下文一拉长、并发一上来就爆显存。总账是三笔相加，不是一笔。
- **“数字精度越高输出一定越好”**：FP16 通常略优，但差距经常小于换一款模型、改一版提示词带来的差距；别为半档精度放弃“能跑得动”这个前提。
- **“本地部署是免费的”**：硬件折旧、电费、折腾时间都是成本；低频使用摊下来，未必比按 Token 付费便宜。
- **“Mac 不能跑大模型”**：统一内存反而是 Apple Silicon 的长处，GGUF 生态跑得很好；只是游戏显卡那套生态（GPTQ/AWQ）基本不在它这边。
- **“上下文窗口设多大都不花钱”**：KV Cache 随上下文长度增长，长上下文是显存大户；窗口开多大，显存就按多大预留。

## 自测问题

### 1. 一款 8B 模型，FP16 和 INT4 各约占多少 GB？这个答案完整吗？

<details>
<summary>查看答案</summary>

权重账：FP16 每参数 2 字节，8 × 2 ≈ 16GB；INT4 每参数 0.5 字节，8 × 0.5 ≈ 4GB。但这只是权重，不是完整答案——运行时还要叠加 KV Cache（随上下文长度增长，GB 量级起步）与框架开销（再留一两 GB），实际占用通常比权重多出好几 GB。只报权重数字，是初学者最常见的不完整答案。

</details>

### 2. GPTQ、AWQ、GGUF 三者是什么关系？Mac 用户大概率选哪个？

<details>
<summary>查看答案</summary>

GPTQ 与 AWQ 是同一层的竞争者：都是训练后量化方法，都主要面向 GPU 推理生态，差别在算法思路（AWQ 对激活分布更友好）。GGUF 是另一层的东西：它是文件格式而非量化方法，llama.cpp 生态的模型文件都存成它，文件名内含量化等级标记。Mac 用户大概率选 GGUF——Apple Silicon 靠统一内存跑大参数量化模型，走的正是 llama.cpp/GGUF 路线。

</details>

### 3. 为什么“上下文拉长”会改变“这块卡带得动”的结论？

<details>
<summary>查看答案</summary>

因为显存总账里只有权重是固定值，KV Cache 随上下文长度增长、随并发数成倍增长。几千 Token 时它可能只是 GB 量级的小头，拉到几万 Token 就能追上甚至超过权重本身，原本“有余量”的配置被吃成“没余量”。所以“带得动”要按你最长的上下文和最大并发来算，不能按最理想的用法算。

</details>

### 4. 哪些信号说明该用本地部署？哪些说明 API 更划算？

<details>
<summary>查看答案</summary>

值得本地（任举三条）：数据敏感不能出本机；离线或网络受限；调用频繁且任务在开源模型能力圈内；已有闲置硬件。API 更划算（任举三条）：要最强能力与最新知识；低频使用摊不薄成本；不想运维；任务对质量波动敏感。两边可以混用——本地小模型做粗活，API 做关键步骤。

</details>

### 5. 批大小（并发数）翻倍，显存里哪部分跟着翻倍？

<details>
<summary>查看答案</summary>

主要是 KV Cache：每个并发请求都要为自己的上下文维护一份 Key/Value 缓存，并发翻倍，缓存总量约翻倍。权重全系统只有一份、所有请求共享，不随并发变化。这正是同一款模型“自己单人用很顺畅、多人同时用就爆显存”的原因。

</details>
